# 오프라인 데이터 수신 계약 v0.1

이 문서는 제안한 파일 입력 규칙이며 APP API가 아닙니다. 다른 형식으로 받은 원본은 보존하고,
단위·시각을 확인한 뒤 변환 사본을 만듭니다. 실제 데이터 없이 CRS, 지도 필드, 보정 행렬,
UFLD 원시 출력 구조를 가정하지 않습니다.

## 1. 주행 세션

```text
data/drives/run_001/
├── recording.json
├── left.mp4
├── right.mp4
├── gps.csv
├── left_frames.csv    # 프레임별 시각을 기록할 수 있을 때
└── right_frames.csv
```

`configs/recording.example.json`을 복사해 사용합니다.

| 항목 | 규칙 |
|---|---|
| `schema_version` | 정수 `1` |
| `session_id` | 주행을 식별할 문자열 |
| `timebase` | `unix_ms`: UTC Unix epoch 기준 밀리초 |
| `gps_path` | 세션 폴더 기준 상대 경로 |
| `cameras` | 1개 이상, 카메라별 메타데이터 배열; 좌우 실험에서는 left/right |
| `camera_id` | 배열 안에서 중복 없는 이름 |
| `video_path` | 세션 안에 있는 비어 있지 않은 원본 파일 경로 |
| `start_timestamp_ms` | 영상 첫 프레임의 측정 시각, 정수; 파일 생성/복사 시각 사용 금지 |
| `frame_timestamps_path` | 프레임별 시각 CSV 상대 경로, 없으면 null |

절대 경로와 세션 폴더 밖을 가리키는 경로는 허용하지 않습니다. 카메라 모델·촬영 모드·해상도·
명목 FPS·시계 정렬 방법은 추가 메타데이터로 기록할 수 있습니다. 추가 필드는 현재 검증하지 않습니다.

가능하면 원본 MP4를 전달합니다. 검증기는 코덱·컨테이너를 디코딩하지 않고 파일 존재만 확인합니다.
MP4 재생 시간은 일반적으로 절대 시각이 아니므로 UTC와의 대응을 기록해야 합니다. 기기 단조 시계,
영상 PTS를 사용했다면 기준 시각·오프셋·시계 오차를 기록하고 변환해야 합니다. 서로 다른 카메라의
시작 시각이 같다고 해서 실제 노출 시각까지 일치하는 것은 아닙니다.

## 2. GPS CSV (UTF-8)

필수 열: `timestamp_ms,latitude,longitude`. 아래 숫자는 **합성 예시**입니다.

```csv
timestamp_ms,latitude,longitude,accuracy_m,speed_mps,bearing_deg
1700000000000,37.4501,126.6531,4.2,8.3,92.0
1700000001000,37.4502,126.6532,,,
```

- 시각은 정수이며 엄격히 증가해야 합니다. 중복 측정은 원본을 보존한 뒤 명시적으로 정리합니다.
- 위도/경도는 WGS84 도 단위로 준비합니다. 수신 데이터가 다른 좌표계이면 확인·변환이 먼저입니다.
- `accuracy_m`와 `speed_mps`는 0 이상, `bearing_deg`는 [0, 360)입니다.
- 선택 열은 생략하거나 빈칸으로 둡니다. 알 수 없는 값을 0으로 채우지 않습니다.
- NaN/Infinity, 잘못된 위경도, 역순·중복 시각, 열 개수 오류는 실패합니다.
- GPS 정확도 값의 의미는 수집 API의 정의도 함께 기록합니다. GPS는 실제 차로 정답이 아닙니다.

## 3. 프레임 시각 CSV (선택, 동기화 검증에는 필요)

```csv
frame_id,timestamp_ms
0,1700000000000
1,1700000000033
```

위 숫자는 **합성 예시**입니다. 두 열 모두 음이 아닌 정수, 엄격한 증가 순서로 기록합니다.
`frame_id`는 해당 영상과 대응되는 인덱스이며, 누락 프레임이 있다면 인덱스의 공백을 허용합니다.
첫 시각은 `start_timestamp_ms`와 일치해야 합니다. 실제 영상 프레임 수·인덱스의 대응 검사는
향후 디코더 단계에서 추가합니다. 단순 FPS 나눗셈으로 만든 시각을 측정 시각으로 표시하지 않습니다.

시각 범위가 GPS 또는 다른 카메라와 전혀 겹치지 않으면 오류입니다. 일부만 GPS 범위에 포함되면
경고입니다. 범위가 겹쳐도 프레임별 동기화 성공을 의미하지는 않습니다. 허용 시각 차이와 프레임
매칭 정책은 실제 장비의 측정값을 보고 결정합니다. 시각 CSV가 없으면 해당 검증은 미확인입니다.

## 4. HD Map

`data/hdmap/`에 원본 구조를 보존합니다. Shapefile은 `.shp/.shx/.dbf/.prj`를 함께 두고,
제공된 `.cpg` 등 다른 동반 파일도 보존합니다. 현재 점검기는 필수 동반 파일 누락을 오류로,
`.cpg` 누락을 인코딩 확인 경고로 출력합니다. CRS가 외부 문서로 제공된 데이터는 좌표계 확인 후
보완해야 하며, 임의의 `.prj`를 만들어 통과시키지 않습니다.

GeoPackage(`.gpkg`)도 원본 그대로 둡니다. 현재 도구는 파일 목록만 확인하며 내부 테이블·CRS를
읽지 않습니다. 지도 출처, 제작 연도, 대상 도로 구간을 별도 메모로 남깁니다. 실제 geometry,
CRS, 속성 이름, 진행 방향, 차로 번호·연결 관계는 후속 지도 조사 단계에서 확인합니다.

## 5. 보정값과 정답

- `data/calibration/`: AI 담당이 실제 카메라로 측정. 렌즈 설정·해상도·장착 상태·좌표축·단위를 기록.
  YAML 템플릿의 null은 미측정 상태입니다. 실제 보정 파일 형식과 파서는 아직 정하지 않았습니다.
- `data/labels/`: 주행 후 사람이 확인한 구간별 차로 및 변경 구간. 추론 입력으로 읽지 않습니다.
  향후 RF 학습 시에만 정답으로 결합하며 주행 세션/날짜/도로별로 학습과 시험을 분리합니다.

## 6. 검사 결과

두 CLI는 JSON을 출력합니다. 오류가 없으면 종료 코드 0, 오류가 있으면 1입니다.
`ok`는 이 단계의 파일/형식 검사만 의미합니다. 경고에 적힌 미검증 항목은 실제 데이터를 열어
확인해야 합니다. 현재 단계에서는 차선 좌표, 후보 점수, 차로 예측을 생성하지 않습니다.
